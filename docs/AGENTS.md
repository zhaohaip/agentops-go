# AGENTS.md

本文件定义 Codex 在当前项目中的工作方式。

项目编码规范、目录规范、设计原则和架构规则统一维护在 `develop-spec/`，本文件只规定工作流程，不重复维护具体规范。

---

# 1. 规范入口

开始任务前，根据修改内容阅读对应规范：

| 修改内容           | 必读文档                                   |
| -------------- | -------------------------------------- |
| Go 代码          | `develop-spec/01-go-coding-guidelines.md` |
| 新增目录/模块        | `develop-spec/02-project-structure.md` |
| 新增抽象、修改依赖      | `develop-spec/03-design-principles.md` |
| 修改模块职责、调用关系、架构 | `develop-spec/04-architecture.md`      |

涉及多个方面时，应同时阅读对应规范。

---

# 2. 工作流程

处理任务时遵循以下流程：

1. 理解任务目标和验收标准。
2. 阅读相关需求、设计和项目规范。
3. 查找已有实现，优先复用。
4. 评估影响范围。
5. 实现最小必要修改。
6. 完成对应测试和验证。

不得仅阅读目标文件后直接修改。

---

# 3. 实施原则

始终遵守：

* 最小必要修改。
* 保持与现有代码风格一致。
* 优先复用已有实现。
* 不扩大任务范围。
* 不进行无关重构。
* 不修改无关代码。
* 不编造业务规则。
* 不隐瞒未验证内容。

发现无关问题，可以说明，但不要顺便修改。

---

# 4. 复杂任务

以下任务应先输出简要实施方案，再开始实现：

* 新功能开发
* 跨模块修改
* 数据库结构调整
* 公共接口修改
* 架构或模块边界调整
* 并发、事务、一致性修改
* 引入第三方依赖
* 大规模重构

实施方案至少包括：

* 修改目标
* 影响范围
* 实现思路
* 风险
* 验证方式

用户明确要求直接实现时，可在方案后继续完成，不必等待确认。

---

# 5. 不确定事项

遇到不确定信息时：

1. 查需求和设计。
2. 查已有实现。
3. 查同类模块。
4. 保守处理。
5. 明确列出假设和待确认事项。

不得自行创造：

* 字段
* 接口
* 配置
* 业务规则
* 状态流转

---

# 6. 验证要求

完成修改后执行与影响范围匹配的验证：

优先：

```bash
gofmt -w <changed-files>
go test <affected-packages>
go vet <affected-packages>
```

必要时：

```bash
go test ./...
go vet ./...
```

无法执行时，应明确说明：

* 未执行项
* 原因
* 已完成验证
* 剩余风险

---

# 7. 文档同步

只有修改影响以下内容时才同步文档：

* 公共行为
* 接口
* 配置
* 模块职责
* 架构
* 目录结构
* 开发规范

文档必须与实际实现一致，不得把计划写成已实现。

---

# 8. 输出要求

完成任务后输出：

* 修改内容
* 影响范围
* 验证结果
* 风险或待确认项

保持简洁，不输出冗长报告。

---

# 9. 子目录规则

若子目录存在自己的 `AGENTS.md`，则同时遵守：

1. 根目录 `AGENTS.md`
2. 最近的子目录 `AGENTS.md`
3. 对应 `develop-spec/` 规范

子目录只记录模块特殊规则，不重复根目录内容。
