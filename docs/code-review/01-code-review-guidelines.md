# 通用代码审核检查表

## 1. 审核类型

审核前必须明确类型：

* `TASK_REVIEW`：审核单个任务是否正确完成；
* `PHASE_REVIEW`：审核多个任务组合后是否达到阶段目标；
* `TARGETED_REVIEW`：复核已发现问题是否完成修复。

小任务 Review 只判断当前任务是否可以完成和提交，不代表整个阶段通过。

## 2. 通用检查项

### 需求实现

* 是否满足任务目标和验收标准；
* 正常、异常和边界流程是否正确；
* 是否存在功能遗漏、错误状态或部分成功。

### 设计与影响范围

* 是否遵守现有架构、模块边界和公共契约；
* 接口、数据结构或配置变化是否同步到相关调用方；
* 是否引入不必要的依赖、重复实现或范围扩张。

### 正确性与安全性

* 输入校验、错误处理、权限和敏感信息处理是否正确；
* 是否存在事务、并发、数据一致性或资源泄漏问题；
* 是否引入明显的兼容性或迁移风险。

### 测试与验证

* 是否具有与变更匹配的测试；
* 是否覆盖核心行为、异常路径和关键边界；
* 是否实际执行相关测试、构建和静态检查；
* 不得将未执行、被跳过或仅编译通过视为验证通过。

### 变更范围

* 区分本次变更新增的问题和仓库既有问题；
* 与当前任务无关的既有问题原则上不阻塞任务；
* 不因个人偏好、未来优化或范围外需求阻塞当前任务。

## 3. 问题等级

* `Critical`：可能造成严重安全、数据损坏或系统不可用；
* `Major`：导致需求未完成、核心行为错误或关键测试缺失；
* `Minor`：局部质量问题，不影响主要功能；
* `Suggestion`：非必需的改进建议。

每个问题必须提供代码位置、触发条件、实际影响和最小修复方向。

## 4. 审核结论

* `PASS`：不存在阻塞当前审核目标的 Critical 或 Major；
* `FAIL`：存在需要先修复的 Critical 或 Major；
* `BLOCKED`：任务范围、需求依据或验证条件不足，无法可靠判断。

结论必须基于实际代码和验证结果，不得只复述开发者说明。

## 5. 审核约束

审核期间：

* 不修改代码和测试；
* 不自动修复问题；
* 不扩大需求范围；
* 不因个人偏好要求重写；
* 不对未检查的代码或未运行的测试作出确定结论。

## 6. 输出要求

审核结果至少包含：

1. 审核类型和最终结论；
2. 实际审核范围；
3. Findings，按严重程度排序；
4. 实际执行的验证及结果；
5. 是否满足验收标准；
6. 是否可以进入提交或下一审核环节；
7. 范围外风险，如无则写“无”。
