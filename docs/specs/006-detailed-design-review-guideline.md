# 详细设计评审 Prompt

请作为一名具备 Go 后端、分布式系统、Agent Runtime 和工程架构经验的 Staff Engineer，对当前详细设计文档进行正式设计评审。

## 一、评审目标

判断当前详细设计是否：

* 完整覆盖需求；
* 符合整体架构约束；
* 模块职责和边界清晰；
* 核心流程完整且可落地；
* 状态、数据和事务设计一致；
* 能够直接指导后续开发；
* 不存在阻塞开发的未决问题。

本次任务是设计评审，不是需求澄清，也不是重新进行详细设计。
将评审结果输出至docs/review目录下

## 二、参考文件

* 需求文档：`docs/design/001-requirements.md`
* 整体架构设计：`docs/design/003-system-architecture-design.md`

评审时必须同时读取以上文件，并以需求文档和整体架构设计作为上位约束。

## 三、评审原则

* 一次性完成全部评审，不要逐个向我提问；
* 不允许假设未明确的需求或设计决策；
* 不直接修改任何文档；
* 不编写代码或伪代码；
* 不重新设计整体架构；
* 不扩大当前详细设计的模块范围；
* 不将个人偏好当作设计缺陷；
* 所有问题必须指出对应依据和实际影响；
* 对无法从文档确认的内容，标记为“待确认”，不得自行补全；
* 对超出 MVP 范围的设计，明确指出并给出裁剪建议。

## 四、重点评审内容

### 1. 需求覆盖

检查：

* 是否覆盖当前模块相关的全部需求；
* 是否遗漏正常流程、异常流程或边界场景；
* 是否引入需求中没有明确要求的功能；
* 是否存在无法满足需求的设计。

### 2. 架构一致性

检查：

* 是否符合整体架构中的模块划分；
* 是否违反既定调用方向；
* 是否出现模块职责越界；
* 是否新增未经架构确认的依赖；
* 是否改变已经确定的关键架构决策。

### 3. 模块职责与边界

检查：

* 每个模块负责什么、明确不负责什么；
* 是否存在职责重叠或职责遗漏；
* 状态修改责任是否唯一；
* 数据写入所有权是否明确；
* 调用方和被调用方的职责是否混淆。

### 4. 核心流程

检查以下流程是否闭合：

* 正常执行；
* Worker 领取；
* Planner 调用；
* Step 执行；
* Tool 调用；
* Approval 等待与继续；
* Cancel；
* Timeout；
* 中断；
* Recover；
* Report 生成。

重点检查每个流程的：

* 前置条件；
* 状态变化；
* 数据写入；
* 事务边界；
* 失败处理；
* 最终结果。

### 5. 状态设计

检查：

* 状态集合是否完整；
* 状态含义是否唯一；
* 状态转换是否合法；
* 转换责任是否明确；
* 是否存在无法退出的中间状态；
* 是否存在状态冲突；
* 是否存在非法回退；
* 终态是否可能被覆盖；
* Task、TaskExecution、Plan、Step、ToolExecution、Approval、Checkpoint、Report 等对象状态是否协调。

### 6. 数据设计

检查：

* 字段是否足以表达设计语义；
* 字段含义和生命周期是否清楚；
* 创建者、更新者和不可变约束是否明确；
* 是否存在一个事实由多个字段重复表达；
* 是否存在字段不足而依赖模糊状态推断；
* 唯一约束、外键或逻辑关联是否明确；
* 历史执行版本是否可以准确审计。

### 7. 并发与一致性

检查：

* 事务边界是否足够短且清晰；
* 是否在事务内调用模型、Kubernetes 或其他外部服务；
* Worker 是否可能重复领取；
* 是否存在并发状态覆盖；
* 是否存在重复执行；
* Command Receipt 幂等语义是否稳定；
* execution_version 和 execution_config_hash 是否被正确使用；
* Checkpoint 与 Recover 是否形成完整恢复链路；
* advisory lock 失效时的处理是否符合架构约束；
* 写 Tool 是否可能因重试产生重复副作用。

### 8. 异常处理

检查是否明确区分：

* 业务拒绝；
* 数据不一致；
* 配置不一致；
* 可安全重做的调用中断；
* 写 Tool 副作用未知；
* 数据库或锁连接失败；
* Runtime 级致命错误；
* 单个 Task 的局部失败。

重点检查：

* 异常是否会造成任务永久卡住；
* 异常任务是否会阻塞 FIFO 队列；
* 是否存在热循环；
* 是否存在错误自动重试；
* 是否可能错误关闭整个 Runtime；
* Report 是否能够获得足够的失败证据。

### 9. 可测试性与可观测性

检查：

* 关键规则是否可以通过测试验证；
* 是否存在难以构造或难以断言的隐式行为；
* 关键失败原因是否有稳定错误码；
* 关键状态变化是否可审计；
* 指标、结构化日志和 Report 的职责是否清楚；
* 是否错误地将最佳努力日志作为唯一事实来源。

### 10. MVP 范围

检查：

* 是否存在明显过度设计；
* 是否引入非必要的高可用、分布式协调或扩展机制；
* 是否增加过多字段、状态或中间抽象；
* 哪些设计可以裁剪但不影响 MVP 核心能力；
* 哪些能力虽然复杂，但属于安全执行所必需，不能裁剪。

## 五、问题分级标准

### Critical

存在以下任一情况：

* 与需求或整体架构直接冲突；
* 可能导致危险副作用或重复执行；
* 可能导致数据不可恢复；
* 核心流程无法闭合；
* 状态或事务设计无法实现；
* 不解决就不能进入开发。

### Major

存在以下任一情况：

* 重要边界没有定义；
* 异常流程存在明显缺口；
* 模块职责不清；
* 可能导致任务卡住、错误恢复或审计缺失；
* 开发前应当修正，但不一定需要改变整体架构。

### Minor

存在以下任一情况：

* 文档表述不清；
* 命名不一致；
* 测试性或可观测性可以加强；
* MVP 可以暂时接受；
* 不影响核心正确性。

## 六、输出格式

# Detailed Design Review Report

## 1. 评审结论

给出以下结论之一：

* ✅ 通过，可以进入开发
* ⚠️ 有条件通过，修改 Critical/Major 问题后进入开发
* ❌ 不通过，当前设计不能指导开发

并用简短文字说明主要原因。

## 2. 设计理解摘要

使用不超过 300 字说明：

* 当前详细设计负责什么；
* 核心流程是什么；
* 与其他模块的主要边界是什么。

该部分用于验证是否正确理解文档，不要大段复制原文。

## 3. Critical 问题

每个问题使用以下格式：

### CRITICAL-01：问题标题

**设计位置：**

指出相关章节、流程、状态、数据表或字段。

**问题描述：**

说明当前设计存在什么问题。

**依据：**

说明与哪条需求、架构约束或已确认决策不一致。

**影响：**

说明可能导致的实际后果。

**修改建议：**

说明应补充或调整的设计方向，不直接代写完整设计。

**是否需要人工确认：**

* 是：列出必须确认的决策点；
* 否：说明可以直接修正的原因。

## 4. Major 问题

使用与 Critical 相同的格式。

## 5. Minor 问题

使用简化格式：

| 编号 | 设计位置 | 问题 | 建议 |
| -- | ---- | -- | -- |

## 6. 需求覆盖检查

| 需求或场景 | 是否覆盖 | 设计位置 | 评审结论 |
| ----- | ---- | ---- | ---- |

仅列出与当前详细设计相关的需求。

## 7. 架构一致性检查

| 架构约束 | 是否一致 | 详细设计表现 | 问题编号 |
| ---- | ---- | ------ | ---- |

## 8. 核心流程完整性

| 流程 | 正常路径 | 异常路径 | 状态闭合 | 结论 |
| -- | ---- | ---- | ---- | -- |

## 9. 状态与数据一致性检查

重点总结：

* 状态转换是否完整；
* 状态写入责任是否唯一；
* 字段是否足够；
* 不可变字段是否明确；
* 是否存在依赖模糊状态推断的设计；
* 是否存在无法审计的关键事实。

## 10. MVP 裁剪建议

分别列出：

* 必须保留；
* 建议裁剪；
* 可以后置。

不得为了简化而裁剪安全执行、幂等、恢复或副作用治理所必需的能力。

## 11. 待确认决策

仅列出文档无法判断、必须由设计负责人确认的问题。

每个问题给出：

* 决策点；
* 可选方案；
* 方案差异；
* 推荐方案及理由。

不要把可以直接从需求或架构中得到答案的问题列为待确认。

## 12. 进入开发前检查清单

使用复选框输出：

* [ ] 所有 Critical 问题已解决
* [ ] 所有 Major 问题已确认或修正
* [ ] 需求覆盖关系已确认
* [ ] 状态转换已闭合
* [ ] 事务边界已明确
* [ ] 幂等与并发规则已明确
* [ ] Recover 与 Checkpoint 规则已明确
* [ ] 异常处理和错误码已明确
* [ ] 模块接口具备开发条件
* [ ] MVP 范围已冻结

## 七、最终约束

* 不要通过连续提问开展评审；
* 一次性输出完整评审报告；
* 不直接修改详细设计文件；
* 不生成代码；
* 不生成实现任务；
* 不重新设计系统；
* 不因为文档篇幅较长而省略关键检查；
* 同一个根因不要重复拆成多个问题；
* 评审重点是正确性、完整性、边界和可实现性，而不是文档格式美观程度。
