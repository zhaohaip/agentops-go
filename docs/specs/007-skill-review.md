# Skill Review 问题处理规则

本次详细设计已经经过 Skill（如 grill-with-docs）评审。

Skill 提出的每一个问题，请不要直接转交给人工确认，而是按下面流程处理：

## 第一步：自主分析

结合以下内容：

- 需求文档
- 整体架构设计
- 当前详细设计
- 已确认的设计原则
- 已确认的历史设计决策

自行分析该问题。

---

## 第二步：判断是否能够自行决策

如果能够推导出唯一合理方案：

- 不需要询问人工；
- 直接选择推荐方案；
- 给出推荐理由；
- 修改详细设计；
- 在最终 Review Report 中记录此次修改。

不要因为存在多个方案就默认需要人工确认。

---

## 第三步：仅在以下情况允许人工确认

只有满足以下任一条件时，才允许输出"待人工确认"：

1. 产品需求本身没有定义；
2. 属于 MVP 范围取舍；
3. 属于技术选型；
4. 多种方案均满足需求，且不存在明显推荐方案；
5. 已确认文档之间存在冲突；
6. 修改将导致整体架构发生变化。

除以上情况外，不允许输出"待人工确认"。

---

## 第四步：修改设计

对于已经能够自行决定的问题：

不要停留在分析阶段。

应当：

- 修改详细设计；
- 更新流程图（如有）；
- 更新状态图（如有）；
- 更新接口设计（如有）；
- 更新事务边界；
- 更新状态转换；
- 更新字段说明。

最终输出修改后的设计，而不是仅给出建议。

---

## 第五步：输出 Review Report

最终 Report 应包含：

### 已自动解决的问题

列出：

- Skill 提出的问题；
- Codex 的分析；
- 最终采用的方案；
- 修改了哪些设计。

### 待人工确认的问题

这里只允许保留真正无法自行决定的问题。

如果能够根据已有设计推导答案，则不得保留。

对于 Skill 提出的设计问题：

默认认为你拥有详细设计负责人的权限。

只要不涉及：

- 产品需求
- MVP 范围
- 技术选型
- 架构升级

你应直接完成设计决策，而不是向人工确认。

如果最终仍输出超过 5 个"待人工确认"问题，则说明 Review 不符合要求，请继续分析，直到只剩真正无法推导的问题。
