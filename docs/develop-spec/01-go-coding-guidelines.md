## Go 编码规范

1. 所有代码必须通过 `gofmt`，并使用 `goimports` 整理依赖。

2. 遵循 Go 惯用写法，优先选择简单、直接、易读的实现，禁止照搬 Java 风格或过度设计。

3. 包名使用简短的小写单词，禁止使用下划线及 `common`、`utils`、`helper` 等含义模糊的包名。

4. 文件名使用小写下划线格式，例如 `task_service.go`。

5. 变量、函数、类型使用驼峰命名；业务变量必须表达明确含义，避免使用 `tmp`、`obj`、`data1` 等模糊名称。

6. 常见缩写保持统一，例如 `ID`、`HTTP`、`API`、`URL`：

```go
userID
httpClient
apiServer
```

7. 接口禁止使用 `I` 前缀；接口应尽量小，并优先由使用方定义。

8. 方法接收者使用简短名称，并在同一类型中保持一致；禁止使用 `this`、`self`。

9. `context.Context` 必须作为函数第一个参数，并沿调用链向下传递；禁止保存到结构体字段。

10. `error` 必须作为最后一个返回值，所有错误必须处理，禁止无理由使用 `_` 忽略错误。

11. 返回错误时应使用 `%w` 补充操作上下文：

```go
return fmt.Errorf("query task: %w", err)
```

12. 使用 `errors.Is` 和 `errors.As` 判断错误，禁止比较错误字符串。

13. 业务代码禁止使用 `panic` 代替错误返回。

14. 优先使用提前返回，减少 `if` 嵌套：

```go
if err != nil {
    return err
}
```

15. 一个函数只处理一个明确职责；函数过长、嵌套过深或包含多个独立阶段时必须拆分。

16. 参数过多时使用明确的参数结构体，禁止使用 `map[string]any` 规避类型设计。

17. 结构体初始化必须优先指定字段名：

```go
task := Task{
    ID:     taskID,
    Status: StatusPending,
}
```

18. 依赖通过构造函数显式注入，禁止新增可变全局变量。

19. 谨慎使用 `init()`；不得在 `init()` 中连接数据库、发起网络请求、启动 goroutine 或执行复杂业务逻辑。

20. 业务代码使用项目统一的结构化日志组件，禁止使用 `fmt.Println` 输出日志。

21. 日志必须包含必要的上下文字段，禁止记录密码、Token、密钥等敏感数据。

22. 同一个错误通常只在决定终止处理且具备完整业务上下文的层记录一次，避免重复日志。

23. 启动 goroutine 前必须明确退出、取消、等待和错误处理机制，禁止启动无人管理的 goroutine。

24. 共享可变数据必须使用 channel、mutex、atomic 或单线程所有权模型进行保护。

25. 禁止使用 `time.Sleep` 解决并发同步问题。

26. 文件、HTTP Body、数据库 Rows、锁、定时器等资源获取成功后必须及时释放。

27. HTTP、RPC、数据库等外部调用必须传递 Context，并设置合理的超时。

28. 重试必须限制次数并使用退避策略；写操作重试前必须确认幂等性。

29. 金额和高精度计算禁止直接使用 `float32` 或 `float64`，应使用整数最小单位或 decimal 类型。

30. 项目统一使用中文注释；涉及专业术语时，可保留官方英文名称（如 Context、Gin、PostgreSQL、Kubernetes、OpenTelemetry 等）。

31. 注释应解释业务原因、边界条件和设计取舍，禁止逐行翻译代码或描述显而易见的实现。

32. 导出的类型、结构体、接口、函数和方法应编写符合 GoDoc 规范的注释，注释内容使用中文。

例如：

// RuntimeHost 表示运行时宿主，负责管理服务生命周期。
type RuntimeHost struct {}

// Start 启动 Runtime Host，并初始化各组件。
func (h *RuntimeHost) Start(ctx context.Context) error

33. TODO、FIXME、NOTE 等开发注释统一使用中文描述，便于团队维护。

例如：

// TODO：支持多实例 Leader Election。
// FIXME：当前仅支持顺序执行。
34. 注释应保持简洁准确，优先说明“为什么这样设计”，避免长篇说明实现过程；复杂设计应记录到设计文档，而非代码注释中。

35. 新增或修改核心业务逻辑时，必须同步补充测试，至少覆盖正常流程、异常流程和关键边界条件。

36. 测试优先使用表驱动方式，禁止依赖测试执行顺序、真实外部服务或长时间 `Sleep`。

37. 禁止为了通过测试而硬编码结果、删除有效测试或修改无关生产逻辑。

38. 禁止引入无必要的第三方依赖、反射、泛型或过度抽象。

39.  禁止修改与当前任务无关的代码，不得擅自进行大范围重构、升级依赖或更改公开接口。

40. 修改代码前必须阅读相关实现、接口、调用方和测试，优先保持项目现有风格和架构边界。

41. 修改完成后必须执行适用的检查：

```bash
gofmt -w .
goimports -w .
go vet ./...
go test ./...
```

项目配置了 Lint 时，还应执行：

```bash
golangci-lint run
```

涉及并发代码时执行：

```bash
go test -race ./...
```

42. 无法执行检查时，必须说明未执行的命令、原因和潜在风险。

43. 未实际执行测试时，禁止声称测试已经通过。
44. go版本：go1.26.3

### 执行优先级

规则冲突时，按照以下优先级执行：

1. 当前任务的明确要求；
2. 当前目录的 `AGENTS.md`；
3. 上级目录的 `AGENTS.md`；
4. 项目现有约定；
5. 本编码规范；
6. Go 官方惯用写法。
