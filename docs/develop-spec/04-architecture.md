## Go 项目架构规范

1. 架构复杂度必须与当前业务规模匹配，优先使用简单、清晰的分层结构，禁止无需求套用 DDD、Clean Architecture 等复杂架构。

2. 中大型项目优先按业务模块组织代码，同一业务的 Handler、Service、Repository 和模型应尽量集中。

3. Handler 作为 Gin 协议适配层，只负责路由参数解析、请求绑定、基础校验、调用 Service 和响应转换，不得包含核心业务逻辑或直接访问数据库。

4. Service 负责业务流程、业务规则和事务边界，是核心业务逻辑的主要承载层。

5. Repository 只负责数据访问和持久化，不得决定业务流程或包含复杂业务规则。

6. 数据库、缓存、消息队列、文件系统和第三方 SDK 必须封装在基础设施或适配层中，不得直接侵入核心业务层。

7. 依赖方向必须清晰，禁止反向依赖和循环依赖。

8. 业务层应依赖所需能力的小接口，具体实现通过构造函数显式注入。

9. 模块之间只能通过公开 Service、最小接口、明确的数据模型或事件交互，不得直接访问其他模块内部实现。

10. HTTP 模型、业务模型、数据库模型和外部 SDK 模型应按实际需要分离，禁止第三方类型贯穿整个项目。

11. 事务由最了解完整业务流程的 Service 层控制，禁止在事务中执行耗时外部请求。

12. 多存储或跨服务操作必须明确一致性、幂等、重试、补偿和并发控制策略。

13. 应用依赖的创建和装配统一放在 `cmd` 或 `internal/app` 中，业务包不得自行创建全局基础设施依赖。

14. 核心业务逻辑必须可独立测试，不应强依赖真实数据库、Redis、MQ 或第三方服务。

15. 禁止创建职责模糊的 `common`、`utils`、`helper` 等公共包。

16. 不得为了未来不确定需求提前新增层次、接口、事件总线、插件机制或复杂设计模式。

17. 修改现有项目时必须保持当前合理架构，不得进行与当前任务无关的大范围重构。

18. 新增模块或架构层前，必须说明其职责、依赖方向和解决的实际问题。
